# Deployment

Everything here assumes a single small server: one owner, one X account. That is
what the system was designed for, and it comfortably fits in about 3 GB of RAM.

---

## 1. Before anything else: understand what you are protecting

Most applications can be restored from their upstream source. This one cannot.

* **X returns `non_public_metrics` only for posts under 30 days old.** Once that
  window closes, the impression figures for those posts exist in your database
  and nowhere else — not in X's API, not in the X web dashboard, not for any
  amount of money.
* **X publishes no follower-history endpoint.** Your hourly follower series
  exists because this system recorded it. Nothing can reconstruct it.
* **X publishes no creator-earnings API.** Every revenue figure was typed or
  imported by you.

So two operational facts follow, and they shape everything below: **the worker
stopping is a data-loss event**, and **backups are not optional**.

---

## 2. Prerequisites

* Docker with Compose v2
* A domain with TLS, terminated by a reverse proxy in front of the stack
* An X developer app with OAuth 2.0 enabled and a redirect URI registered
* Optionally an Anthropic API key. Without one, collection, analytics, alerts
  and reports all still work — agent runs finish as `PARTIAL` with no insights.
* Optionally SMTP credentials. Without them, alerts and reports are generated
  and readable in the dashboard but nothing is emailed.

---

## 3. Configuration

```bash
cp .env.example .env
make setup          # generates SECRET_KEY, TOKEN_ENCRYPTION_KEY and a DB password
```

Then edit `.env`. The production validator refuses to boot on several of these,
which is deliberate — a misconfigured deployment should fail loudly at startup
rather than quietly at 3am.

| Variable | Notes |
|---|---|
| `ENVIRONMENT` | `production`. Turns on the startup guards, HSTS and host validation, and disables `/docs`. |
| `SECRET_KEY` | ≥32 chars. Generated by `make setup`. |
| `TOKEN_ENCRYPTION_KEY` | base64url of exactly 32 random bytes. **See key rotation below before you change it.** |
| `ALLOWED_HOSTS` | Comma-separated **hostnames** this API answers to, e.g. `api.example.com,backend`. Not URLs — a `Host` header has no scheme, so an origin here rejects every request. Required in production. |
| `FRONTEND_ORIGIN` | Must be `https://` in production. |
| `COOKIE_SECURE` | Must be `true` in production. |
| `POSTGRES_PASSWORD` | Generated by `make setup`. |
| `X_CLIENT_ID` / `X_CLIENT_SECRET` | From your X developer app. |
| `X_REDIRECT_URI` | Must match the URI registered with X exactly. |
| `X_MONTHLY_BUDGET_USD` | The cost governor's ceiling. Start at 25 and watch the Overview page. |
| `X_ENABLE_WRITE_ACTIONS` | Leave `false` until you have used the approval queue. With it off, `tweet.write` is never requested, so the stored token cannot publish. |
| `ANTHROPIC_API_KEY` | Optional. |
| `SMTP_*`, `ALERT_EMAIL_*` | Optional. Email is off unless host, from and to are all set. |

## 4. Deploy

```bash
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec backend python -m app.cli create-owner
```

The `migrate` service runs `alembic upgrade head` to completion before the API,
worker or scheduler start, so nothing ever comes up against a schema it does not
expect.

Only the frontend publishes a port, and only on `127.0.0.1`. Point your reverse
proxy at it and terminate TLS there — the app sets HSTS but cannot terminate TLS
itself. Postgres and Redis are reachable on the internal network only.

Then open the dashboard, connect your X account, and check the Overview page:
collection health, the capability matrix and projected monthly spend are all
there.

**Connect the account sooner rather than later.** Posts already older than 30
days when you connect can never have their impressions recovered.

## 5. Backups

The database is the system of record for data that cannot be re-fetched. Treat
losing it as losing the account's history permanently.

```bash
make backup              # writes ./backups/xagent-YYYYmmdd-HHMMSS.sql.gz
```

Put that on a cron job, off the machine:

```cron
15 3 * * *  cd /srv/xagent && make backup && \
            rclone copy backups/ remote:xagent-backups/ --max-age 25h
```

Restore into an empty database:

```bash
make restore FILE=backups/xagent-20260809-031500.sql.gz
```

Two things worth testing **before** you need them:

1. That the restore actually works. An untested backup is a hypothesis.
2. That your retention outlives the time it takes you to notice a problem. If
   you check the dashboard weekly, seven daily backups is not enough margin.

## 6. Monitoring

The system monitors itself, and the alert that matters is `COLLECTION_STALLED`:
it fires when the hourly snapshot has not run for six hours, escalates to
CRITICAL at twenty-four, and describes data being lost as you read it. Configure
SMTP so that one can reach you when you are not looking at the dashboard.

Beyond that:

| Signal | Where |
|---|---|
| Liveness / readiness | `GET /api/v1/health/live`, `/ready` |
| Collection health, gaps, posts near the 30-day cliff | Overview page, and `GET /api/v1/collection/{id}/health` |
| API spend against the ceiling | Overview page, and `GET /api/v1/x/usage` |
| Agent runs, stage timings, rejected citations | Agent Activity |
| Alert delivery outcomes | Agent Activity → "Where alerts go" |

Logs are structured JSON on stdout. Ship them wherever you ship logs; the
scrubber redacts credential-shaped keys at any depth before anything is emitted.

## 7. Upgrades

```bash
git pull
make backup                                              # always, first
docker compose -f docker-compose.prod.yml up -d --build
```

The `migrate` service applies any new migrations before the rest restart. Every
migration has a tested `downgrade()` — `tests/test_postgres.py` runs the full
downgrade and re-upgrade against real PostgreSQL — so a bad release can be
rolled back:

```bash
docker compose -f docker-compose.prod.yml run --rm migrate alembic downgrade -1
```

Roll back the code to match, or the ORM will expect columns that no longer
exist.

## 8. Key rotation

`TOKEN_ENCRYPTION_KEY` encrypts the X OAuth tokens at rest with AES-256-GCM.
There is deliberately no automatic re-encryption: changing the key without
re-encrypting makes the stored tokens undecryptable, and the system cannot tell
that apart from tampering.

To rotate: disconnect the X account in the dashboard (which deletes the stored
tokens), change the key, restart, and reconnect. Collected history is untouched
by this — only the credentials are encrypted.

`SECRET_KEY` can be rotated freely; it invalidates active dashboard sessions and
nothing else.

---

## 9. Running the tests against production-shaped infrastructure

The suite runs on in-memory SQLite by default and needs no setup. A second pass
against real PostgreSQL covers what SQLite cannot — JSONB types, timezone-aware
datetimes, concurrent unique-constraint arbitration, and the migrations
themselves:

```bash
createdb xagent_test
TEST_POSTGRES_URL='postgresql+asyncpg://postgres@localhost/xagent_test' pytest
```

Without `TEST_POSTGRES_URL` those tests skip, so `pytest` stays a single
no-setup command.

---

## 10. Scaling, and when not to

This is a single-account system, and the schema is multi-tenant-ready rather
than multi-tenant. Before scaling out, note:

* **`beat` must stay at one replica.** Two schedulers double every collection
  job and every API charge.
* **`worker` can scale horizontally.** Snapshots are keyed by
  `(post_id, captured_at)` and the constraint is enforced by the database, so
  duplicate work is rejected rather than duplicated — `tests/test_postgres.py`
  demonstrates two concurrent transactions racing for the same row.
* **The X API is the real ceiling**, not this application. Reads are billed per
  resource, and the cost governor degrades the collection cadence as the budget
  tightens — while never skipping the pre-cliff freeze, because that data cannot
  be re-acquired.
